# 重生细胞（B站版）res.pak 结构逆向 — 实测结论

包名 `com.bilibili.deadcells.mobile` 3.5.14-bilibili / arm64-v8a / Android 16
样本 `assets/res.pak` = 409,837,687 B（另有 res1~res4.pak，合计 1.65 GB）

## 1. 文件头 76 字节（明文）

| 偏移 | 长度 | 含义 |
|---|---|---|
| 0 | 4 | magic `PAK\x01` |
| 4 | 4 | u32 LE dir_len = 33880（尾部区域长度）|
| 8 | 4 | u32 LE payload_len = 409803807 |
| 12 | 64 | ASCII hex stamp hash（256-bit）|

自校验：`dir_len + payload_len == filesize` ✅ 完全成立

## 2. 尾部区域 [filesize-33880, filesize)

目录区的**加密副本**。末尾 1112 字节为明文（动画帧数据：`Intern.png` / `Idle_0..15` + 8×u16）。
帧数据格式：`u16 x, u16 y, u16 w, u16 h`（后续字段待定）

## 3. payload @76 — 目录表（明文）

```
6 字节   00 01 01 00 00 00
1+n      长度前缀根名 "atlas"
1        tag = 0x01
4        u32 LE 条目数 = 913
```

条目（stride = 13 + name_len）：
```
1   name_len
n   name
5   零填充
4   u32 LE table_offset（payload 内偏移）
4   u32 LE hash
```

## 4. 资源记录流（核心发现）

起点在 payload+4113 附近（可用最长链扫描定位），记录紧密相连：

```
u32 LE abs_offset   文件内绝对偏移
u32 LE size         数据大小
u32 LE hash         校验值
u8     name_len
bytes  name
u8     0x00         NUL 结束符
stride = 14 + name_len
```

res.pak 中成功连续解析 **801 条**记录（abs 严格递增，零断裂）。

## 5. 数据加密状态

- 逐文件加密，熵 ≈ 7.0（非 zlib、无标准魔数）
- 少数条目含明文 ASCII 片段（如 `"0, 59, 43"`）
- **未解出加密算法** — 需要分析 `libnative-lib.so` 中的
  `mobile_android_assets_FileSystem_loadPak` / `hxd_fmt_pak_FileSystem_get`

## 6. 对「动态加载 mod」的意义

- ✅ 目录/索引结构已完全掌握 → 可以定位任意资源
- ✅ 条目数为 913、记录格式确定 → 可以**新增条目**
- ❌ 数据加密未解 → 无法直接替换/新增资源内容
- ⚠️ 目录区有加密副本 + 64 字节 stamp hash → 改动后有校验风险

### 1. 「仅储存方式导入」= 完全正确 ✅

引擎 **导入 `AAssetManager_openDir` + `AAssetDir_getNextFileName`**（9 个 AAsset* 导入），

→ 所以「按序号追加 res5.pak」在引擎侧成立：新 pak 会被 addPak 累加进虚拟文件系统。

### 3. 「需要加密 res5.pak」= **与实测不符，可能是误记** ⚠️
我实测 **res.pak ~ res4.pak 的数据区全部是明文**：

→ **pak 本身没有加密**。若游戏对 *新增* pak 有额外加密要求，那也不在现有 5 个包上体现。

**结论**：pak 格式是**明文**的；「加密」这一步在当前证据下**不需要**。
若你去年确实做了加密才能生效，那说明存在**另一条校验路径**（可能是 PakUtils.getPakStampHash
对 *未在 base 中的新 pak* 的额外要求），需要进一步实测确认。

### pak 加载机制（已定论）
- **硬编码循环**：`res.pak, res1.pak, res2.pak, ...` 直到 `android_fs_assets_exists` 返回 false
- 这解释了为什么 res5.pak 能生效（从最后一个序号继续）✅ 用户说法再次正确
- **但只从 APK 内 `assets/` 找** —— 加外部目录不生效，除非改 `assets_exists`/`File_read` 行为

## 加载器可行的唯一缝隙
循环体是两个可 Hook 的点：
1. `android_fs_assets_exists(path)` → 让外部路径返回 true
2. `mobile_android_assets_File_read(path)` → 从外部读 pak
两者都在 `libnative-lib.so` 内，且都是**导出符号**（PLT 可达）。
→ 这就是用户去年第三/四阶段要 Hook 的目标，**目标找对了，卡在 W^X 无法改内存**。

## Java 层加载缝隙（新发现，去年未记录）
| dex | 加载 |
|---|---|
| classes5.dex | `libnative-lib.so` |
| classes6.dex | `libmain.so`（SDL2 glue，仅 NEEDED SDL2/GLES/OpenSLES）|

`libmain.so` 是 4056B 的 NDK r29 转发壳，由 SDL 标准 `SDLActivity` 加载。
→ Java 层早加载（`<clinit>`/`onCreate`）在**重打包 APK 时**可行，
  但这仍属「装一次」，之后换 mod 不需重装 —— 正是用户要的形态。

## 结论
- 免重装 = **装一次带 loader 的 APK**，之后 mod 放外部目录
- loader 需要 Hook 两个导出函数 → **非 root 下受 W^X 限制**（用户去年已撞墙）
- 仍需验证的路径：**在重打包 APK 时注入 loader 的 .so 并让它在 libnative-lib 之前加载**，
  用 PLT/GOT 改写的是**自己进程内的 GOT**（同进程可写），而非改代码段 —— 这条路未被试过

## 【重大突破】ReLinker 缓存机制 —— mod 不生效的真正根因 (2026-09-30 04:15)

### 决定性实验

把 `libmain.so` 换成一个**必然加载失败**的 so(引用未定义符号 `this_symbol_does_not_exist_xyz`),
重装后启动游戏 → **游戏崩溃**,崩溃栈:

```
java.lang.UnsatisfiedLinkError: dlopen failed: cannot locate symbol
  "this_symbol_does_not_exist_xyz" referenced by
  "/data/data/com.bilibili.deadcells.mobile/app_lib/libmain.so"
  at java.lang.System.load(System.java:1729)
  at com.getkeepsafe.relinker.SystemLibraryLoader.loadPath(SystemLibraryLoader.java:31)
  at com.getkeepsafe.relinker.ReLinkerInstance.loadLibraryInternal(ReLinkerInstance.java:206)
  at com.getkeepsafe.relinker.ReLinkerInstance.loadLibrary(ReLinkerInstance.java:136)
  at com.playdigious.deadcells.mobile.DeadCellsLoading.onCreate(DeadCellsLoading.java:31)
```

### 结论:游戏加载路径是 `app_lib/`,而且是 ReLinker 解包的缓存副本

1. **加载入口**:`DeadCellsLoading.onCreate:31` → ReLinker → `System.load(app_lib/libmain.so)`
2. **不是**直接加载 APK 内 `/lib/arm64/libmain.so`,而是 **ReLinker 先解包到 `app_lib/`**
3. **ReLinker 只在 `app_lib/libmain.so` 不存在时才解包** —— 存在就直接用旧副本
4. 所以:**换 APK 里的 libmain.so 后,必须清掉 app_lib 缓存**,否则永远跑旧版

### 验证过的事实
- boom.so (5688B) → 崩溃 ✅ (因为触发了重新解包)
- probe.so (6128B) → 无日志 ❌ (app_lib 里是旧副本)
- v2 modsrv.so (10904B) → 无日志 ❌ (同上)

### 修复方法
```
cmd package clear com.bilibili.deadcells.mobile   # 清 app_lib, 触发 ReLinker 重解包
```
**但副作用:清缓存会丢失登录态**(需重新登录 B站)。

### 对比:为什么 03:23 那次成功?
那次是 `-r` 覆盖安装且**没有清缓存**,而当时 app_lib 里恰好是 v1 loader
(因为更早的一次安装已经把它解包进去了)。所以是**时机巧合**,不是机制正确。

# 外载 Mod 加载器 —— 成功 (2026-09-30)

## 结论
**不用重装 APK、不用改包,把 pak 丢进外部目录即可生效。**

APK 里只有 `res.pak`~`res4.pak`(已用 `unzip -l` 确认无 res5),
而引擎日志显示 `res5.pak` 被成功外载 -> 证明加载来自外部目录。

## 落盘位置(按优先级)
```
/sdcard/Android/data/com.bilibili.deadcells.mobile/files/DeadCellsMods/
/storage/emulated/0/Android/data/com.bilibili.deadcells.mobile/files/DeadCellsMods/
/sdcard/DeadCellsMods/                          (作用域存储下通常不可读)
```
**必须用第一个**:Android 11+ 作用域存储下,`/sdcard/` 根目录即使有
READ_EXTERNAL_STORAGE 也**只能 stat 不能 open**(实测 EACCES)。
App 自己的 external files 目录**无需任何权限**。

## 加载链(反汇编确认)
```
Boot_initRes
 -> mobile_Res_initAssets (0x16267f4)
      path = "res"+i+".pak"
      if (!assets_exists(path)) break          <- 闸门 A
      fd = File_read(path, 0)
      addPak(fd)
        -> android_fs_assets_read (0x277f8f8)  <- 闸门 B
        -> Reader_readHeader -> haxe_io_Input_readString
```
注: `res.pak` (i=0) 是无条件直读的,不进 assets_exists 检查。

## 引擎内部表(关键)
`android_fs_assets_read` 的返回值**不是系统 fd**,是三张平行表的**索引**:

| 表 | 偏移(相对模块基址) |
|---|---|
| AAssetManager* | `0x2e8f630` |
| FILE* 表 | `0x2e8f638` |
| 起始偏移表 | `0x2e91638` |
| 长度表 | `0x2e93638` |
| 分配 hint | `0x2e95638` |

步长 `0x2000` = 1024 槽 × 8 字节。

⚠ **偏移必须按「页地址 + 页内偏移」算**:
```
adrp x9, 2e91000      -> x9 = 0x2e91000 (已是页地址)
add  x9, x9, #0x638   -> x9 = 0x2e91638 (不是 0x2e910638!)
```

## 实现要点
hook 两个 **C 层**函数(GOT 改写,`mprotect(RW)` 可突破 RELRO):
1. `android_fs_assets_exists(name)` -> 外部有则返回 1(否则循环提前退出)
2. `android_fs_assets_read(path, mode)` -> 自己 fopen + 填三张表 + 返回索引

**不要**自己合成 Haxe 对象(v4 死在这里):
类型指针必须用 `base+0x2854d10`(File 类),布局是 `fd@+12 / length@+20`。
交给引擎自己的 `File_read` 构造对象最稳。

⚠ `File_read` 传给 `assets_read` 的 **mode 是 1**(不是 0):
```
22eb3cc: cbz  x1, 22eb43c   ; arg1 == NULL
22eb43c: mov  w20, #1
22eb3f0: mov  w1, w20
```
所以守卫条件**不能**写 `if (!mode)`。

## 部署流程(顺序很重要!)
```bash
# 1. 装 APK(只需一次)
cmd package install -r -d ext7.apk
# 2. 清数据
cmd package clear com.bilibili.deadcells.mobile
# 3. ★清数据会连 external 目录一起删, 所以 mod 必须在这之后再放
D=/sdcard/Android/data/com.bilibili.deadcells.mobile/files/DeadCellsMods
mkdir -p $D && cp res5.pak $D/
chmod 666 $D/res5.pak && chmod 2777 $D   # 保留 setgid, 否则 log 读不出来
# 4. 启动
monkey -p com.bilibili.deadcells.mobile -c android.intent.category.LAUNCHER 1
# 5. 看日志
cat $D/loader.log
```

## 日志
- 落盘: `<mod目录>/loader.log`(不依赖 logcat —— logcat 缓冲会被启动日志冲掉)
- logcat tag: `DCMOD`(不可靠,仅辅助)
