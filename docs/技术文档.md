## 1. 成果与使用方式

### 1.1 核心突破

`libmain.so` 是游戏启动时**必定加载**的原生库(由 ReLinker 从 APK 解出后 `System.load`)。
把它替换成自己的加载器,构造函数就在**游戏进程内**执行 —— 于是可以:

- 用自己的 `dl_iterate_phdr` + `PT_DYNAMIC` 解析找到引擎基址
- 改写引擎的 **GOT**(`.got.plt`)把 `assets_exists` / `assets_read` 换成自己的实现
- 从外部目录读 pak 文件,交给引擎自己的文件表

**只需安装一次**带加载器的 APK,之后加 mod 完全不用碰安装包。

### 1.2 对用户的操作

```bash
# ① 装一次带加载器的 APK (只需一次)
cmd package install -r -d DeadCells-外载Mod版.apk

# ② 把 mod 放进这个目录(唯一需要记的路径)
/sdcard/Android/data/com.bilibili.deadcells.mobile/files/DeadCellsMods/

# ③ 进游戏即生效。不用重装、不用清数据
```

用 `modctl.py` 一条命令搞定:

```bash
python3 modctl.py push res5.pak     # 推送 mod
python3 modctl.py list              # 看当前有哪些 mod
python3 modctl.py log               # 看加载器日志
```

> ⚠ `modctl.py` 必须走 **shell 通道(uid 2000)**;
> 普通 bash 进程(uid ~3540)受作用域存储限制,**看不到** `/sdcard/Android/data/`。

### 1.3 mod 文件怎么来

「外载」只解决**怎么加载**,pak 内容本身还是要自己改。做 pak 有两种路线:

| 路线 | 做法 | 适用 |
|---|---|---|
| **覆盖 pak** | 造 `res5.pak` 等编号更大的包,同名资源自动覆盖前面的 | 改数值表(推荐) |
| **换 data.cdb** | 只替换 `data.cdb` 这一个文件 | 改配置表 |

引擎是**累加覆盖**语义: 按 `res.pak, res1.pak, ...` 顺序加载,
**后加载的同路径资源覆盖先加载的**。所以做个 `res5.pak` 塞进改过的
`data.cdb` 即可,完全不用动原有 5 个大包。

## 2. PAK 格式

### 2.1 文件头(76 字节)

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0 | `char[3]` | 魔数 `"PAK"` |
| 3 | `u8` | 版本 = 1 |
| 4 | `u32` LE | `headerSize` |
| 8 | `u32` LE | `dataSize` ( = 文件大小 − headerSize ) |
| 12 | `char[64]` | **ASCII-hex 校验戳** |

### 2.2 目录树(从 headerSize 偏移开始，注意是**从 76 起算的相对偏移**)

```
根节点:
  u8  x = 0
  u8  y = 1
  u8  topCount
  u8[3] pad

条目 (Entry):
  u8    nameLen
  char  name[nameLen]
  u8    flags
  if (flags & 1):                     # 目录
      u32 childCount
      Entry children[childCount]
  else:                               # 文件
      if (flags & 2): f64 pos         # 大包用 8 字节偏移
      else:           u32 pos
      u32 size
      u32 extra
```

**真实数据偏移 = `headerSize + pos`**

### 2.3 关键事实

- 全部 `assets/res*.pak` 在 ZIP 里是 **STORED(method 0)**,未压缩未加密,明文。
- **校验戳每个游戏版本不同** —— 改包必须用同版本的原包做参考。
- 游戏**不校验**这个戳(实测改写后能正常跑),但保持正确更稳妥。

### 2.4 校验戳参考值

| 版本 | stamp |
|---|---|
| 3.5.9 | `1300133c828af0e744d8ae01c6d8887c7e8f0c8b3e6edbdb36a2c3ad9b7ad05e` |
| 3.5.14 | `be9b51cab13f0a0c0f5ccf0512d5e2f6f8661b771743b050d1be108ed2460c7f` |

### 2.5 各 pak 规模(3.5.9 与 3.5.14 完全一致)

| pak | 条目数 | headerSize | 3.5.9 数据大小 |
|---|---|---|---|
| res.pak | 913 | 33,880 | 409,837,687 |

## 3. 引擎加载链(反汇编)

全部地址基于 **3.5.9 的 `libnative-lib.so`**(基址相对偏移)。

```
Boot_initRes
 └─ mobile_Res_initAssets                    @ 0x16267f4  (668 B)
      │
      ├─ [i=0] 直读 res.pak  ← 无条件, 不检查存在性
      │     File_read("res.pak") -> addPak
      │
      └─ loop i = 1, 2, 3, ...
            path = "res" + itos(i) + ".pak"     @ 0x1626898
            utf8 = hl_utf16_to_utf8(path)       @ 0x16268c4
            ok   = assets_exists(utf8)          @ 0x16268c8  ← 闸门 A
            if (!ok) break                      @ 0x16268cc
            fd   = File_read(path, 0)           @ 0x1626914
            addPak(fd)                          @ 0x1626920
            i++                                 @ 0x1626924
```

### 3.1 `mobile_android_assets_File_read` @ 0x22eb3bc

```asm
22eb3c8:  mov  x19, x0            ; x19 = path (Haxe String)
22eb3cc:  cbz  x1, 22eb43c        ; ★ arg1 == NULL -> 跳
22eb43c:  mov  w20, #1            ; ★ w20 = 1  (即 mode=1!)
22eb3e0:  ldr  x0, [x19, #8]      ; x0 = String->bytes (UTF-16)
22eb3ec:  bl   hl_utf16_to_utf8
22eb3f0:  mov  w1, w20            ; ★ mode = 1
22eb3f4:  bl   android_fs_assets_read
22eb408:  adrp x0, 2854000
22eb40c:  ldr  x0, [x0, #3344]    ; File 类类型指针 = base+0x2854d10
22eb410:  bl   hl_alloc_obj       ; 构造返回对象
22eb418:  stp  w20, wzr, [x0,#12] ; ★ fd     @ +12
22eb42c:  str  w8,  [x19,#20]     ; ★ length @ +20
```

**返回对象布局**: `+0` 类型/vtable、`+12` fd、`+20` length。

### 3.2 `android_fs_assets_read` @ 0x277f8f8 (584 B)

它做三件事: 打开 asset → `fdopen` → **注册进三张内部表**，返回**表索引**。

```asm
277f958:  AAssetManager_open(mgr, path, 0)
277f978:  AAsset_openFileDescriptor(asset, &start, &length)
277f98c:  fdopen(fd, "rb")           -> x21 = FILE*
277f9b4:  w20 = *HINT                 ; 从 hint 起找空槽
277f9d8:  loop: if (T_FILE[i]) i++    ; 扫到 NULL
277fad4:  T_OFFSET[i] = start
277fae0:  T_FILE[i]   = FILE*
277fae4:  T_LENGTH[i] = length
277fb00:  return w20                  ; ★ 返回的是索引!
```

找不到时按错误类型返回负数(`-2` ~ `-6`)。

### 3.3 `fd_*` 系列(全部把参数当**表索引**)

| 函数 | 地址 | 行为 |
|---|---|---|
| `fd_get_length` | 0x277fb40 | `return T_LENGTH[i]` |
| `fd_seek` | 0x277fb50 | `fseek(T_FILE[i], T_OFFSET[i]+rel)` |
| `fd_tell` | 0x277fb80 | `ftell(T_FILE[i])` |
| `fd_close` | 0x277fbcc | `fclose(T_FILE[i]); T_FILE[i]=0; OFFSET/LENGTH[i]=-1` |
| `fd_read_bytes` | 0x277fcfc | `fread(buf,1,n,T_FILE[i])` |

**这是整个项目最关键的认识**:返回值不是系统 fd。把它当 fd 用必崩。

## 4. 外载原理

### 4.1 为什么能改 GOT

引擎用 `-Wl,-z,now` 链接(`BIND_NOW` + `FLAGS_1=NOW` + 全 `GNU_RELRO`)，
看上去"不可 hook"。但实测:

```c
mprotect(page_of_got_slot, PROT_READ|PROT_WRITE)  // rc = 0 (成功!)
```

**RELRO 只是把数据页设成只读,不是不能改**。作为游戏自己的进程,
`mprotect` 提权完全合法 —— 这推翻了早期"GOT 不可改"的错误结论。
(早期 xHook 失败是因为它改的是**代码段**,那才是真正的 W^X 墙。)

### 4.2 加载器怎么进场

```
DeadCellsLoading.onCreate:31
  -> ReLinker.loadLibrary("main")
       -> 把 APK 的 lib/arm64-v8a/libmain.so 解到 app_lib/
       -> System.load("/data/data/<pkg>/app_lib/libmain.so")
```

`libmain.so` 原始只有 3,864 字节、零个非 UND 导出、无 `INIT_ARRAY`,
纯粹是 SDL2 胶水,而且 `libnative-lib.so` **不从它导入任何符号** —— 替换绝对安全。

### 4.3 两个 hook 点

```
assets_exists(name)            <- 闸门 A, 决定循环是否继续
  外部有同名 -> 返回 1 (否则引擎认为没有 res5.pak, 循环直接退出)

assets_read(path, mode)        <- 实际读取
  外部有同名 -> 自己 fopen + 填三张表 -> 返回合法索引
```

**只 hook `File_read` 是不够的**(v2 的失败): 引擎先问 `assets_exists`,
返回 false 就 `break`,`File_read` 根本不会被调用。

### 4.4 为什么外载目录必须在 App 私有目录

Android 11+ 作用域存储下,即使 manifest 里有 `READ_EXTERNAL_STORAGE`:

| 路径 | stat | open | 说明 |
|---|---|---|---|
| `/sdcard/DeadCellsMods/` | ✅ | ❌ EACCES | 任意目录被拦 |
| `/sdcard/Android/data/<pkg>/files/...` | ✅ | ✅ | **无需任何权限** |

实测日志:
```
assets_exists("res5.pak") -> stat 成功但 open 失败 (/sdcard/DeadCellsMods/res5.pak): Permission denied
```

所以加载器按优先级尝试三个目录,取第一个真能开的:
1. `/sdcard/Android/data/<pkg>/files/DeadCellsMods/`  ← 用这个
2. `/storage/emulated/0/Android/data/<pkg>/files/DeadCellsMods/`
3. `/sdcard/DeadCellsMods/` (兼容,通常不可用)

## 5. 引擎内部表(核心难点)

### 5.1 布局

全部相对模块基址:

| 表 | 偏移 | 类型 |
|---|---|---|
| `AAssetManager*` | `0x2e8f630` | 指针 |
| **FILE\*** | `0x2e8f638` | `FILE*[1024]` |
| **起始偏移** | `0x2e91638` | `int64[1024]` |
| **长度** | `0x2e93638` | `int64[1024]` |
| **分配 hint** | `0x2e95638` | `int32` |

**步长 `0x2000` = 1024 槽 × 8 字节**，四张表全部落在 `.bss`(末端 `0x2e994c0`)。

### 5.2 ⚠ 最容易踩的坑: `adrp` 的页地址

```
adrp x9, 2e91000          ; x9 = 0x2e91000 ← 这已经是【页地址】
add  x9, x9, #0x638       ; x9 = 0x2e91638 ← 不是 0x2e910638!
```

`adrp` 装载的是 **4KB 对齐的页地址**,不是完整地址。多读一位就差 0x100000。

**自洽校验法**: 相邻表间隔必须恰好 `0x2000`。
如果算出来是 `0x20000`(10 倍),就是错了。
另一个旁证: `AAssetManager*` 在 `0x2e8f630`,表首在 `0x2e8f638`,正好隔 8 字节。

### 5.3 运行时自检

加载器启动时会打印表指针和未打开槽位的初值,地址算错会**立刻暴露**
(而不是等 `fd_*` 解引用时崩):

```
[thread] 表: FILE=0x75d32fd638 OFFSET=0x75d32ff638 LEN=0x75d3301638 HINT=0x75d3303638
[thread] 自检 T_FILE[0..15]: 16 空 / 0 非空
[thread] 自检 T_LENGTH[0..7] = 0,0,0,0,0,0,0,0
```

再者: 内置 pak 占槽 `0..4`,外载正好拿到 `idx=5` —— 若地址算错绝不可能是这么干净的值。

## 6. 加载器实现

源码见 `01_加载器/modsrv.c`(约 380 行,单文件无依赖)。

### 6.1 结构

```c
__attribute__((constructor))
modsrv_init()                      // 进场, 起 hook 线程
  └─ hook_thread()                 // 轮询等引擎加载
       ├─ dlopen("libnative-lib.so", RTLD_NOLOAD)   // 等它出现
       ├─ dl_iterate_phdr()                        // 拿模块基址
       ├─ 解析 PT_DYNAMIC -> SYMTAB/STRTAB/JMPREL
       ├─ hook_sym("android_fs_assets_exists")
       └─ hook_sym("android_fs_assets_read")
```

### 6.2 GOT 改写

```c
static void **find_got(uintptr_t base, const char *sym) {
    // 遍历 PT_DYNAMIC 取 DT_SYMTAB / DT_STRTAB / DT_JMPREL / DT_PLTRELSZ
    // 扫 R_AARCH64_JUMP_SLOT, 比对符号名
}

static int hook_sym(uintptr_t base, const char *sym, void *hook, void **orig) {
    void **slot = find_got(base, sym);
    long pg = sysconf(_SC_PAGESIZE);
    uintptr_t a = (uintptr_t)slot & ~(pg - 1);
    mprotect((void*)a, pg, PROT_READ|PROT_WRITE);   // ★ RELRO 可破
    *orig = *slot;
    *slot = hook;
    mprotect((void*)a, pg, PROT_READ);
}
```

### 6.3 外载核心

```c
static int my_assets_read(const char *path, int mode) {
    // ★ 不要按 mode 过滤! initAssets 传的是 mode=1
    char ext[600];
    if (ext_for(path, ext, sizeof ext)) {     // 外部目录里有同名文件?
        FILE *fp = fopen(ext, "rb");
        int idx = 找空槽();
        g_tfile[idx]   = fp;
        g_toffset[idx] = 0;                   // 普通文件起始即 0
        g_tlength[idx] = 文件长度;
        return idx;                           // 返回索引, 引擎自己会用
    }
    return real_assets_read(path, mode);      // 否则走原函数
}
```

### 6.4 日志

写 `<mod目录>/loader.log`,**不依赖 logcat**。
原因: 游戏启动瞬间日志量极大,4 MiB 的 logcat 缓冲会把早期输出冲掉 ——
这曾导致"加载器明明跑了却看不到日志"的误判。

### 6.5 编译

```bash
export LD_LIBRARY_PATH=$PREFIX/lib
$PREFIX/bin/clang -shared -fPIC -O2 -o libmodsrv.so modsrv.c \
    -llog -ldl -lpthread
```

> bionic **没有 `dlinfo`**,必须用 `dl_iterate_phdr` + 手动解析 `PT_DYNAMIC`。

## 7. 踩过的坑(5 个真实故障)

按发现顺序,每个都曾导致"mod 不生效"或崩溃。

### 坑 1 — 只 hook `File_read` (v2)

**现象**: 完全无反应,连日志都没有外载记录。
**原因**: 引擎先调 `assets_exists(path)`,APK 里没有 `res5.pak` → 返回 false →
`break` → `File_read` 永远不会被调用。
**修法**: 必须**同时** hook `assets_exists`,外部有文件就返回 1。

### 坑 2 — 自己合成 Haxe 对象 (v3/v4)

**现象**: 弹窗 `Can not read asset at [res5.pak]`,或崩在
`addPak -> Reader_readHeader -> haxe_io_Input_readString`。
**原因**: 两个错:
1. 类型指针借了 `path` 参数(Haxe String)的 vtable,应该是 File 类
   (`base+0x2854d10`);GC/方法调用按类型处理必然崩。
2. 结构体偏移写成 `fd@+16 / length@+24`,实际是 `fd@+12 / length@+20`。
**修法**: **不要自己造对象**。改 hook C 层的 `assets_read`,
让引擎自己的 `File_read` 去构造对象 —— 类型和偏移都不可能错。

### 坑 3 — 把返回值当系统 fd (v4 崩溃真因)

**现象**: 崩在 `fd_read_bytes` / `fd_get_length`。
**原因**: `assets_read` 返回的是**三张内部表的索引**,不是系统 fd。
把 `open()` 的 fd(=223)当索引去 `T_FILE[223]` → 读到垃圾指针。
**修法**: 照抄引擎的注册逻辑 —— 自己 `fopen` 然后填三张表,返回索引。

### 坑 4 — `adrp` 页地址多读一位 (v5)

**现象**: 崩在 `hook_thread` 自身,`SEGV_ACCERR`,fault addr 恰好是 `T_HINT`。
**原因**: 把 `adrp x9, 2e91000` + `add x9, x9, #0x638` 算成 `0x2e910638`,
正确是 `0x2e91638`。
**定位方法**: 寄存器 dump 是铁证 —— `x4` = fault addr = 我算的 T_HINT,
`x11 = 0x2e910638` 正是错值;步长应是 `0x2000` 而不是 `0x20000`。
**修法**: 用页地址 `0x2e91000 + 0x638`;并加运行时自检。

### 坑 5 — `mode` 守卫写反 (v6)

**现象**: `assets_exists` 生效,`assets_read` 却没被调用 → 依旧 File Not Found。
**原因**: 反汇编显示 `initAssets` 传的 `mode` 是 **1**(不是 0):
```asm
22eb3cc:  cbz  x1, 22eb43c
22eb43c:  mov  w20, #1
```
而守卫写成 `if (!mode && path)` → 恰好把唯一要拦的调用挡在门外。
**修法**: 不按 `mode` 过滤,只要外部有同名文件就接管。

### 附带坑 — `cmd package clear` 会删 external 目录

**现象**: 清数据后 mod "消失"。
**原因**: `clear` 连 `/sdcard/Android/data/<pkg>/` 一起清。
**修法**: **顺序必须是** `clear` → 再 `push` mod。

### 附带坑 — `chmod` 破坏 setgid 导致日志读不出

**现象**: 明明有日志,shell 读不到。
**原因**: `chmod 777` 会清掉 setgid 位,目录变普通 `drwxrwxrwx`,
游戏进程(uid 13548)写的文件组变成 `u0_a3548`,而 shell(gid 1078=ext_data_rw)读不了。
**修法**: 用 `chmod 2777` 保留 setgid。

### 9.1 3.5.9 vs 3.5.14

**pak 结构、条目数、headerSize 完全相同** —— 工具链无需任何改动,只有 stamp 不同。

### 9.2 3.5.14 新增的安全库

`libanogs.so`(腾讯 ACE)、`libtapsdkcore.so`、`libthemis.so`、`libopencv_java4.so`;
移除 `libweibosdkcore.so`;`libcrypto_1_1.so` → `libcrypto.1.1.so`(同名改法)。

> 关于"3.5.14 是否加了安全补丁": **加固措施确实增加了**,
> 但 `BIND_NOW` + 全 RELRO 这道墙**在 3.5.9 就已存在**(标准 NDK 配置),
> 不是版本新增的。而且实测该墙**可以绕过**(见 §4.1)。

### 9.3 3.5.9 的 dex 结构

3 个 dex:`classes.dex` (9,086,304) / `classes2.dex` (7,989,820) / `classes3.dex` (7,227,656)。
`DeadCellsLoading` + ReLinker 相关字符串全在 **`classes3.dex`**。

3.5.9 的启动 Activity **未导出**,`am start` 会 `SecurityException`,
需用:
```bash
monkey -p com.bilibili.deadcells.mobile -c android.intent.category.LAUNCHER 1
```
